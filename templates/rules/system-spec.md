# 系統規格書規則

## 目的
- 系統規格書用於快速理解整個系統是做什麼、服務誰、包含哪些主要模組與流程。
- 系統規格書是系統層文件，不取代單一需求的 `srs.md`。
- 單一需求文件需能追溯回系統規格書描述的範圍、模組或流程。

## 基本原則
- 文件內容以整體系統為範圍，不聚焦單一功能細節。
- 不可將未確認資訊寫成事實。
- 若資訊不足，先列出待確認問題，再產出草稿。
- 系統規格書需能幫助新成員快速理解系統目的、邊界、核心流程與相關需求。
- 全專案遵守單一語言原則（支援 `zh-TW`、`en`、`zh-CN`、`ja`、`ko`），非繁體中文專案的標題與 Metadata 標籤依專案鎖定語言呈現（可透過 `sa-spec templates system-spec` 取得對應語言骨架）。

## 文件位置
- 建議檔名為 `project/system-spec.md`。
- 若未來需要版本化，可再調整為獨立資料夾，但第一版先以單檔管理。

## 文件欄位與結構
### 1. 初始標準骨架（由 `sa-spec init` 建立）
- Metadata 標頭：
  - `狀態`：`草稿`、`待確認`、`已審核`。
  - `主要語言`：鎖定語言（例如 `繁體中文 (zh-TW)`、`English (en)`）。
  - `規範版本`：目前 `@loviusc/sa-spec` 規範版號。
  - `合併策略`：`auto-merge`（預設，歸檔後自動切回主分支合併、推送並刪除已合併 feature 分支；若遠端主分支受保護則自動退回保留分支）或 `pr`（只推 feature 分支供 PR 審核，不動主分支）。
- 核心章節：
  - `這個系統要解決什麼`：系統摘要與主要解決的問題。
  - `使用者`：主要使用者與角色清單。
  - `主要需求`：核心功能範圍與已歸檔/規劃中的需求清單。
  - `待確認`：尚未拍板之系統級待確認事項。

### 2. 隨需求演進可擴充之建議子章節
隨需求於 `spec:commit` 確認歸檔並更新 `project/system-spec.md` 時，視系統複雜度補充以下子章節：
- 業務目標、範圍與不在範圍。
- 系統邊界與主要功能模組。
- 核心流程總覽與關鍵資料主題。
- 外部系統與介接、非功能需求總覽。
- 已知限制與假設、相關需求清單（`REQ-xxx`）。
- 估算總覽。

## 模組描述要求
- 每個主要模組需說明其目的、主要使用者與支援的業務情境。
- 若模組已拆成多個需求，需列出對應需求編號。

## 流程描述要求
- 核心流程以總覽層級描述，不展開到每個按鈕或欄位細節。
- 若流程涉及跨模組、跨系統或權限切換，需特別標示。

## 估算要求
- 系統規格書需提供整體估算總覽，詳細規則遵守內建估算規則（可透過 `sa-spec rules estimation` 查詢）。
- 若估算前提未確認，估算狀態需標示為 `待確認`。

## 待確認事項
- 待確認事項不可混入正式規格內容。
- 每個待確認事項需說明影響範圍，例如模組、流程、估算或驗收。
- 待確認事項解決後，需同步更新相關需求文件與 `history.md`。
