# 人工審核規則

## 審核原則
- 每份文件產出後都停留在人工審核點。
- 未經人工確認的文件狀態不得標示為 `已審核`。
- 審核時優先確認 AI 是否加入未經確認的假設。
- 任務開始前應先說明任務目標與任務清單；完成前應分別核對「流程檢查清單」與「業務檢查清單」。

## 流程檢查清單（Process Checklist）
- 是否已在開始前說明任務目標並依任務清單逐項執行。
- Git 分支、remote 推送與遠端主分支同步（`git fetch`）是否已完成。
- 是否已完成既有 `REQ-*` 與 `project/system-spec.md` 衝突檢查。
- 交付物目錄與檔名是否完整（`srs.md`、`uml/`、`openapi.yaml`、`db-schema.md`、`handoff.md`、`history.md`）。
- `uml/` 是否遵守單檔單圖原則，且含 UI 需求已提供 `uml/wireframe.puml`（純後端已於 `handoff.md` 標註無 UI）。
- `{{REQ_ID}}` 佔位符、鎖定語言純淨度與 `sa-spec check --strict` 是否皆已通過。

## 業務檢查清單（Business Checklist）
- 需求目標、業務範圍與預期價值是否清楚且無歧義。
- 使用者角色、權限矩陣與資料存取邊界是否明確。
- 主要流程、例外流程、失敗重試與權限不足情境是否完整。
- 業務規則、計算邏輯與狀態機轉換是否有明確來源或待確認標示（未擅自假設）。
- SRS、UML、OpenAPI（request/response/狀態碼）與 DB Schema（欄位/約束/關聯）業務契約是否一致。
- 驗收條件是否具體可測試，且高風險注意事項與版本歷程已正確記錄。

## 通用審核清單
- 需求目標是否清楚。
- 使用者與角色是否明確。
- 主要流程是否完整。
- 例外流程是否足夠。
- 功能需求是否可驗收。
- 非功能需求是否有必要且可衡量。
- 業務規則是否有來源或待確認標示。
- 高風險注意事項是否已記錄。
- 歷程文件是否已更新。

## UML 審核清單
- UML 是否對應需求編號。
- UML 是否與 `srs.md` 一致。
- UML 是否新增了未確認角色、流程或系統行為。
- UML 是否標示待確認內容。

## Wireframe 審核清單
- Wireframe 是否對應需求編號。
- Wireframe 是否只根據 `srs.md` 或已標示待確認的內容產出。
- 畫面目的、畫面元素、操作流程與錯誤狀態是否清楚。
- 欄位、按鈕、連結、提示文字與錯誤訊息是否有用途。
- 空狀態、載入狀態、錯誤狀態與權限不足狀態是否足夠。
- 權限或角色差異是否明確。
- 是否影響 API request / response、DB Table 欄位或驗收條件。
- Wireframe 發現的 SRS 缺口是否已回寫待確認事項。

## API、DB Table 與資料模型審核清單
- API 或資料模型是否只根據已確認需求產出。
- 權限、錯誤處理與資料欄位是否明確。
- 是否有影響既有 API 或資料結構。
- 是否需要更新 UML、驗收條件或注意事項。
- DB Table、欄位、Index、Constraint 是否能追溯到需求。
- Nullable、Unique、資料保留、刪除規則是否明確。
- Migration、資料轉換、rollback 與效能風險是否已評估。
